# docker-devkit

## What this is

`docker-devkit` owns the Docker-stack lifecycle commands — `up`, `down`, `build`, `mirror`, `generate-score`, `docker-build-matrix`. A small, generic package that any repo shipping a compose graph can depend on to get the same bring-up/tear-down / cross-build flow, with the compose assembly declared per consumer in the `lifecycle:` section of `docker-devkit.yaml`. The PyPI identity starts its own version tags at `0.1.0`; the terminal `stack-toolkit` distributions (≤0.1.1) are deprecation signposts pointing here, not this package's history.

The package is `docker_devkit` (src-layout under `src/docker_devkit/`); all dependencies resolve from PyPI — `bashrun` (shell-outs), `build-artifact-registry` (builds-shelf push and ORAS provisioning for CI artifacts), `packaging` (`requires` specifier parsing), `pathspec`, `pydantic`/`pydantic-settings`, `pyyaml` (score-document parsing), `strictyaml` (config loading), `typer` (CLIs) — git-source pins only in scratch branches testing unreleased changes.

Config follows the org law (home: github-actions-toolkit's `AGENTS.md`): this is a root-`docker-devkit.yaml` devkit. The schema (`config.DockerDevkitConfig`, strictyaml-loaded, `extra="forbid"` on every model) carries a required `requires` version stamp plus optional `lifecycle` / `mirror` / `generate-score` sections; `config.load_config` self-checks the installed docker-devkit version against `requires` and refuses loudly outside the range (the `0.0.0.dev0` dev sentinel bypasses the check, not the field).

## Release flow

github-actions-toolkit's `AGENTS.md` owns the consumer workflow contract; this repo follows it unchanged. Repo-specific facts: github-actions-toolkit is never a project dependency (docker-devkit sits inside its own dependency graph; a project-level edge is a resolver cycle), and from 1.0 on API-breaking changes ship with a manually bumped `major_minor` (pre-1.0, breaking changes ride the patch flow; patch-auto assumes additive changes).

## Mirror consumption

Consumers with docker images (placeframe, capture-tool) run `mirror` via the docker-devkit PyPI dependency — inline in their `mirror-images` job (checkout + `setup-uv` + ghcr login + `uv run mirror`), version-sourced by the consumer's `uv.lock`. The job carries `permissions: { contents: read, packages: write }` + `env: GITHUB_TOKEN` (ghcr login for `crane copy`). Pure-Python devkits have no `mirror-images` job.

## Shape

Entry points (`[project.scripts]`): `up` → `compose.py:up_app`, `down` → `compose.py:down_app`, `build` → `build_docker.py:app`, `mirror` → `mirror.py:app`, `generate-score` → `score_generate.py:app`, `docker-build-matrix` → `matrix.py:app`. All accept `--help`.

| Module | Role |
|---|---|
| `compose.py` | The `up` and `down` typer apps over one shared preamble. `_compose_invocation()` runs it: lifecycle-config load and bake-declaration enforcement, `.env` presence plus the manifest-paired image lock (required only when a manifest exists; the lock's `--env-file` leg is dropped without one), gpu resolution, tree-sha env injection, compose-file assembly, and the `docker compose -f … --project-directory … --env-file .env` command prefix. `up` flags: `--attached`/`-a`, `--quiet-pull`/`-q`, `--build`, `--gpu auto\|cuda\|rocm\|none`, `--dev` (requires `dev_file`). `up` resolves `COMPOSE_PROFILES` (shell env over `.env`, comma-split, deduped), rejects values naming profiles the compose files don't define, and forwards the selection as explicit `--profile` flags — compose ignores the variable whenever any flag is present, so forwarding is the only reliable path. With a mirror section declared, `up` fail-closed probes every lock entry (imagetools) before bring-up. `down` flags: `--volumes`/`-v` (also removes named volumes), `--gpu`; it always layers the dev overlay and activates every profile declared across the assembly (via `config --profiles`), so teardown covers containers from a prior bring-up under a different `COMPOSE_PROFILES` selection. |
| `build_docker.py` | `run_build()` + the `build` command — cross-builds all images per the resolved image manifest, writing the paired lock (one `NAME={prefix}/{ref}@sha256:…` entry per upstream-native `x-base-images` declaration, the mirror-prefixed form derived from `mirror.prefix`; `@digest`-pinned declarations pass through unresolved; digests resolve against the upstream reference). `--push` is the CI shape (push images + registry caches + digest-manifest shelving) and hard-requires `x-registry-cache`; the flag order mirrors the binding's run line (`--push`, `--targets`, `--gpu`), and `--targets` accepts both repeated flags and one space-joined value. Push mode reads its registry facts from the neutral `REGISTRY`/`REGISTRY_TOKEN`/`REGISTRY_USERNAME` environment — no `GITHUB_*` reads. |
| `score_generate.py` | `generate-score` — deterministic Score-manifest generation from a consumer's `stack/score/` sources: `${ALL_CAPS}` placeholder expansion into tempdir-rendered workload copies, idempotent `score-compose`/`score-k8s` init, and a determinism suite (document sort, state-path normalisation, instance-suffix hash rewrite, 0644 modes, LF newlines). Provisioner files are compiled from authored mapping form first (`provisioners.py`); both renderings wrap their init+generate in that compile so `--provisioners` always points at the per-run compiled copies. The image lock beside the manifest (`bake_file`'s `.lock` pair) is loaded once per run and threads through both pre-passes, so authored lock markers (see `markers.py`) resolve at generation in provisioner manifests and chart values alike. Both tool state dirs are per-run temp: score-k8s mints a random `instance_suffix` per workload and stamps it into the manifests, so the suffixes are rewritten to name-derived hashes and the state dirs are torn down after generation — nothing stateful is committed and output reproduces from a fresh clone. The pinned tools must already be on `PATH` (fetched per the release links; `helm` joins them when charts are declared); `generate-score` refuses loudly listing the exact versions, since output differs between releases. The compose output gets a bind-inlining post-pass: score-compose materialises workload `files:` as bind mounts into its gitignored state dir (a generate-and-run-here model), so every `type: bind` volume is rewritten into a top-level `configs.content` entry — the invariant is zero host-filesystem references in the committed artifact; a bind that cannot be resolved and read (`.score-compose/…` sources resolve against `score_dir`, everything else against the repo root the way compose resolves it at runtime; absolute paths and directories are loud errors) kills generation, and literal `$` doubles to `$$` so consumer interpolation leaves `${VAR}` (loki) and `{$VAR}` (caddy) alone. The command splits into one stage helper per rendering plus contract enforcement (`generate_compose`, `generate_k8s`, `enforce_secret_contract` — public because tests drive them) and the multi-caller shared helpers (`_init_state`, `_rendered_workloads`, `write_generated_file`); every other single-production-caller fragment inlines into them (unit tests are not callers), so tests exercise the stage helpers, the entry point, and multi-caller helpers only. Consumer policy — workloads, provisioners, patch templates, output paths, storage classes, publishes, tool versions — is declared in the consumer's root `docker-devkit.yaml` under `generate-score:` (`ScoreConfig`, model in `config.py`); `ensure_score_tools()` fetches the pinned score-compose/score-k8s/helm release binaries (for CI staleness gates; helm's archive nests its binary under `linux-amd64/`, so its extract strips one component). `charts:` entries in the section render at generation through `helm template` against the org-mirrored form of their digest-pinned upstream-native OCI ref (charts declared with no `mirror:` section is a loud error) and merge into the same kind/namespace/name-sorted manifests — helm is a renderer, never a deployer; a chart's values files are consumer-committed paths resolved against the repo root: a marker-free file passes to `--values` untouched, and a file carrying markers gets an include- and lock-resolved copy written into the per-run tempdir (preserving the file's subpath so same-named values files cannot collide) for `--values` to read; `namespace` is per-chart (helm stamps it into rendered docs), and a chart failing its own validation fails generation loudly. A `secrets:` section declares the tier-neutral secrets contract (see `secrets.py`): after the renderings this run generated, each artifact's consumed keys are validated as a subset of the declaration, and the mint list artifact is written from the declaration alone. Output and state paths resolve against the repo root: the compose half runs in `score_dir` (its `.score-compose` state dir is created there during the run and removed after), the k8s half runs in the configured `k8s_state` parent, same teardown. `--local` writes the k8s artifact to the configured gitignored local path with the local storage class. |
| `provisioners.py` | The provisioner authoring format and its compiler. Authored provisioner files carry `state`/`outputs`/`volumes`/`services` as real YAML mappings and `manifests` as a real list (`AuthoredProvisioner`, `extra="forbid"`) — score's string form is YAML-in-a-string that no editor highlights or linter parses, so it is generated, never authored. A field already in string form is a loud validation error naming the law (the compiled output must never be pasted back into a source). `compiled_provisioners(source_dir, names, root)` compiles each registered file into a per-run tempdir *under `score_dir`* — the compiled form never touches the committed tree, and the `--provisioners` paths stay POSIX-relative to the repo layout instead of encoding any machine's temp location; subdirectory names (`compose/`, `k8s/`) are recreated inside the tempdir. Compilation and the artifact/value dumps share `ComposeDumper` and its `dump_compose()` wrapper (`sort_keys=False`, literal blocks for multiline strings), so authored key order controls dump order at every level; `${VAR:?err}` holes and `{{ env }}`/`{{ .State }}` templates survive as inline string values, multiline strings dump as literal blocks, and comments are dropped (the authored file keeps them — the compiled form is ephemeral). The compile pre-pass resolves include markers (see `markers.py`) against the repo root, then lock markers against the loaded image lock, both before validation — so a ConfigMap body sources a committed config file instead of hand-mirroring it, and an authored image reference resolves to the lock's digest instead of a hand copy. ConfigMap content fields that are not includes stay strings: they are scalar values inside `manifests`, not the provisioner format itself. |
| `markers.py` | The authoring-marker resolvers shared by the provisioner compile pre-pass and the chart-values pre-pass. A marker is a single-key mapping — single-key mappings keep authored sources plain-YAML-parseable (no custom tags), which is the authoring format's lintability goal. `include: <repo-root-relative path>` inserts the file's bytes verbatim as a string scalar; `include-yaml: <path>` parses the file and inserts the structure (charts like grafana's demand mapping-shaped values); neither mode transforms content — `${VAR}` holes pass through untouched; `$`-handling is per-consumer (the compose converter doubles `$`, k8s-side inclusion never does). Paths anchor at the repo root (matching how binds reference `workloads/…`); absolute paths and `..` escapes are loud errors, as are missing files, non-string marker values, invalid or empty YAML includes, and include cycles. `include-yaml` trees resolve recursively with cycle detection; text content is never scanned for markers. Lock markers run in the same two pre-passes after include resolution (included structure can carry lock markers): `lock: NAME` substitutes the entry's full `workloads/images.lock` reference, making the lock the single digest source for k8s provisioners (which have no runtime env-file to fill compose-style `${VAR}` holes); `lock-image: NAME` expands the entry into the `registry`/`repository`/`tag`/digest fields chart values want (the standard chart convention: registry is the path minus the last component, joined back into the same reference). Charts that spell the digest field `sha` (grafana's, bare hex — its template re-adds the `sha256:` prefix) declare `lock-image: {key: NAME, digest_field: sha}`. Include resolution and lock resolution stay separate sequential passes — inclusion can introduce lock markers, and text includes stay opaque to lock scanning. The lock is the manifest's `.lock` pair, loaded once per generation run by the `generate-score` entry point; unknown entry names, non-string marker values, malformed spec mappings, and non-digest-pinned references under `lock-image` are loud errors, as are malformed or duplicate lock lines. `contains_marker` is the predicate the values pre-pass uses to pass marker-free files through untouched. |
| `secrets.py` | The tier-neutral secrets contract. A consumer-committed declaration (`generate-score.secrets.file`, a `KEY: description` mapping — or `KEY: {description: …, mint: true}` for keys that ride the externally managed k8s Secret named by `k8s_secret`) lists every key either rendering consumes; after generation, each rendering's consumed keys must be a subset of it (subset, not equality — pair-variance is legitimate). Compose consumption is `${ALL_CAPS}` brace holes with odd `$`-parity in the artifact (`$$`-escaped configs.content doesn't count); k8s consumption is `secretKeyRef` entries naming the configured Secret (wholesale `envFrom`/`extraEnvFrom` `secretRef`s impose no per-key constraint). The mint list artifact (`secrets.output`, one key per line under a provenance comment) generates from the declaration alone, so deploy-time Secret recipes and the Pulumi sync read a generated list instead of a hand copy. |
| `config.py` | `DockerDevkitConfig` — the root `docker-devkit.yaml` schema: a required `requires` PEP 440 specifier plus optional `lifecycle` / `mirror` / `generate-score` sections, `extra="forbid"` on every model. `load_config(root)` is the single strictyaml entry point: parses the file (returns `None` when absent — the no-config → single-file-default path for `up`/`down`), then self-checks the installed docker-devkit version against `requires` (refuses loudly outside range; the `0.0.0.dev0` dev sentinel bypasses the check, not the field). The section models (`LifecycleConfig`, `MirrorConfig`, `ScoreConfig`, `SecretsConfig`, `ChartConfig`) live here; `ChartConfig` refs are digest-pinned upstream-native OCI references (parse-time validation kills the unpinned-chart failure mode), `ScoreConfig` requires `helm_version` plus unique chart names when charts are declared, and `SecretsConfig` (the optional `secrets` key) wires the declaration path, the Secret name k8s validation scopes to, and the mint output path; `load_mirror_config` in its module is a thin wrapper over it. |
| `lifecycle.py` | `LifecycleConfig` (model in `config.py`) — the `lifecycle:` section declaration (`files`: compose files in layering order with `{gpu}` templating; `dev_file`: optional dev overlay); `require_manifest()` / `resolve_manifest()` (the raising form) over the named manifest/lock pair `workloads/images.yml` + `workloads/images.lock` (`MANIFEST_PATH`/`LOCK_PATH`; callers join the lock path directly); `enumerate_profiles()` (asks compose for every profile the assembly defines — `down`'s teardown set and `up`'s existence-check source); `detect_gpu()` → `cuda`/`rocm`/`none` from host devices (the `Gpu` literal; `GPU_TYPES` = the concrete variants), and `parse_env_file()` (the shared `.env` reader, imported externally by consumer scripts). |
| `matrix.py` | `docker-build-matrix` — emit the CI build leg list as a bare JSON array on stdout (the binding's getter pipes it through its `matrix` verb, which composes the envelope and guards the empty case): one entry per variant × cohort cell, `targets` = that cell's explicitly-buildable services with dependents grouped with the base their `additional_contexts: target:` references pull in (one leg builds a whole dependency-closure group in a single bake invocation). The leg schema — `targets` (space-joined), `variant` (`common`/`cuda`/`rocm`, from the service-name suffix) — is named contract with the binding; renaming a key breaks its fanout YAML. The cross-compile cohort (services in `x-cross-compile-targets` or declaring `platforms:`) gets its own legs — per-arch builds are the QEMU-slow ones and parallelize away from native builds; a group spanning cohort membership is a loud error. Tagless services never become explicit targets (bake rejects a tagless target under `--push`) — they ride as in-invocation dependencies; a group spanning gpu variants is a loud error. |
| `documents.py` | `BakeDocument` + `parse_bake(path)` — the typed bake-file model every consumer of bake data goes through (build, up, down, generate-score, the reference collectors). A field validator enforces at parse time that every `x-base-images` value is `path:tag` or `path@digest` (a `${…}` hole or a bare path is a validation error, killing the silent-unpinned `FROM` → `:latest` failure mode). `compute_service_shas(repo_root, bake: BakeDocument)` — per-service `tree-<hash>` image tags over the `.dockerignore`-allowlisted git tree. The workload-tree root is derived as the single top-level directory containing every tagged service's Dockerfile (a bake graph spanning several top-level directories is a loud error); files under it that belong to no tagged service are excluded from every SHA rather than shared into all of them. |
| `image_refs.py` | Image-reference collection, split by source. `unpinned_references(root)` scans Dockerfile `FROM`, Dockerfile `COPY --from=` (slash-bearing captures only, so build-stage names are skipped), and yaml `image:` lines — hand-written literal refs that bypass the declaration system — across the `workloads/` and `docker/` Dockerfile trees and the `stack/score/` + `score/` source trees, and polices exactly what it finds (every slash-bearing reference must carry a tag, a digest, or a trailing `${build-arg}` suffix — consumer CIs fail on its result). `bake_base_image_refs(bake: BakeDocument)` adapts declarations to `ImageReference` pairs; `version_coupling_violations(root, couplings)` (each `VersionCoupling` names a pyproject-declared version and the `VersionSite` regexes that must restate it — bake `x-base-images` values or raw file text — so non-derivable couplings like uv `required-version` ↔ uv-base-image tag can't drift silently; the mechanism lives here, the registry in consumer repos' preflight) is unchanged. Remote digest resolution goes through `imagetools inspect`. Compose files are parsed by nothing in this package. |
| `mirror.py` | The mirror namespace's config, injection, and verbs. `MirrorConfig` (model in `config.py`, the `mirror:` section, key `prefix`), `load_mirror_config()` (reads the `mirror:` section via `config.load_config`, `None` when the section or file is absent), `mirrored_ref` (prefix injection with the double-prefix guard), and the `mirror` verb (enumerates bake `x-base-images` declarations from `workloads/images.yml` — parsed and validated via `BakeDocument`, the single source consumer mirroring consumes — plus crane install and one `crane copy {ref} {prefix}/{ref}` per declared reference — the set includes the `generate-score:` section's chart declarations, whose OCI refs copy byte-identically so mirror and upstream digests are equal; count footer). Constraints in "Mirror namespace". |

## Lifecycle declaration contract

`up`/`down` assemble the graph from the `lifecycle:` section of the consumer's root `docker-devkit.yaml` — one code path, declared data. Keys: `files` (compose files in layering order, `{gpu}` templating, a `{gpu}` entry dropped when the GPU resolves to `none`; defaults to empty), `dev_file` (dev overlay, appended by `up --dev` and always by `down` so teardown removes containers from prior dev bring-ups). No section → single-file default (`-f compose.yml`). `--compose-file` does not exist; raw `docker compose` is the pressure valve. `--dev` is opt-in — production-shaped bring-up is the default. The image lock is required exactly when an image manifest exists — the lock is the manifest's resolved pair, and a repo whose whole graph arrives via published compose bundles has neither: `up`/`down` skip the lock requirement and its `--env-file` leg. Manifest-bearing repos pin stock images via `${…_IMAGE:?err}` holes filled by a committed lock. An image manifest present under either resolved name without a lifecycle declaration is a hard error (declare the section, or the file doesn't belong under that name) — guards are budgeted for silent failures only, and a missing lock already fails loudly. The manifest remains the build/up contract: SHA injection and `--build` acceptance key on the manifest existing, and `build` always reads the resolved manifest. `up`/`down` pass `--project-directory` (the invocation root) explicitly, so compose files living in nested trees (`stack/generated/compose/`, overlays) anchor their relative paths at the repo root instead of the first `-f` file's directory. An empty assembly (`files` empty/omitted, no dev overlay) is a loud `up`/`down` error — the honest state for a builds-only repo (a repo with no repo-local runtime graph omits the section and is refused loudly if `up`/`down` run).

placeframe's shape lives in placeframe's `docker-devkit.yaml`, not in this package: a `lifecycle` section with `files` = `compose.yml`, `compose.postgres.yml`, `compose.{gpu}.yml` (in layering order) and `dev_file` = `compose.dev.yml`.

Profile-gated services are selected solely by `COMPOSE_PROFILES`; the verbs hold no built-in profile names. `up` fails loudly on a selection naming undefined profiles (the silent alternative is a stack that comes up minus its gated services); `down` ignores the selection and enumerates everything defined, since teardown must cover prior bring-ups under other selections.

`--quiet-pull` suppresses compose's per-layer progress (CUDA images carry hundreds of layers) while still surfacing pull totals. `--gpu auto` resolves to `cuda`/`rocm`/`none` from host devices and selects the matching `compose.<gpu>.yml`; override only to reproduce a CI environment or test the CPU-only path.

## File and env conventions the commands assume

- `.env` (required) — carries `COMPOSE_PROFILES` (the sole service selector `up`/`down` consult) plus whatever variables the consumer's compose files interpolate.
- `workloads/images.lock` (required exactly when `workloads/images.yml` exists, checked in) — third-party and base-image pins, written by `build`: one `NAME={prefix}/{ref}@sha256:…` entry per manifest declaration. `up`/`down` refuse a manifest-bearing repo without it; consumers satisfy it with a committed lock filling the `${…_IMAGE:?err}` holes. The lock sits beside its manifest as the resolved pair.
- `workloads/images.yml` (where a local build graph exists, required) — the image manifest and buildx-bake description; its top-level `x-cross-compile-targets` list (optional) is the set of services excluded from the default target list because they need per-arch treatment, opt-in via `--targets`. `build` reads exactly one manifest: `workloads/images.yml`. `buildx bake` resolves the manifest's relative paths against its invocation cwd, so `build` always invokes from the repo root.
- the compose layers declared in the `lifecycle:` section of `docker-devkit.yaml`; the GPU one is picked by `detect_gpu()` (or the `--gpu` override).
- `.dockerignore` (where images are built locally) — allowlist that `documents.py` hashes over to compute per-service `tree-<hash>` tags. See "Docker build context" in `AGENTS-SHARED.md` for the allowlist rationale.

`build` injects the `tree-<hash>` tags of locally-built images into the environment rather than writing them anywhere; `up`/`down` do the same via `compute_service_shas`. The lock stays a pure third-party pin file — a CI invariant forbids built-image digests in the committed, reviewed lock.

## Mirror namespace

Third-party images are consumed through an org-owned mirror namespace (`ghcr.io/outernet-foundation/mirror/<upstream-host>/<path>…`) instead of pulling upstream registries directly: manifests at upstream get GC'd, and an upstream yank once broke external cloners — digest pins alone don't save you when the manifest is gone. Durability for strangers beats upstream egress: strangers, CI, and prod always pull the mirror. Populating it is CI's job, single writer — engineers never push to the org namespace, and error text must never teach them to (no "run this populate command" hints).

Declarations are upstream-native and the mirror-prefixed form is derived: `x-base-images` values spell the upstream reference, and the `mirror:` section's `prefix` in the consumer's root `docker-devkit.yaml` is the single place the namespace is named. `mirrored_ref(reference, prefix)` is the only join — it injects the prefix and rejects an already-prefixed reference (the double-prefix guard: drift toward the namespace is a loud error, never a silent skip). Declaring `x-base-images` with no `mirror:` section is a hard `build` error; the `mirror` verb requires the section outright. Under the section:

- `build` resolves lock digests against the upstream reference and records each entry under the derived mirror name (`NAME={prefix}/{ref}@sha256:…`). Valid because `crane copy` produces byte-identical manifests — upstream and mirror digests are the same digest; a manifest re-wrap (`docker buildx imagetools`-shaped tooling) would change the top-level digest and break lock equality. This makes declare → re-lock walkable before CI has mirrored anything; lock lines are never hand-authored.
- `up` fails closed: it probes every lock entry (each is mirror-prefixed by construction); a missing mirror image is a hard `RuntimeError`, not a warning — people ignore warnings, and warnings are errors someone was too lazy to fix. There is no escape flag: a missing entry means the declaring change has not been through CI's mirror job yet, and the fix is to let it run. CI ordering never wants the escape — the mirror job runs before anything needs the images. The probe's stderr is classified before an error is reported: only a registry 404 / manifest-unknown verdict gets the not-mirrored error; an unauthorized or transport failure (stale registry credentials, network, daemon down) is reported as a probe failure carrying the underlying error text, so a host-side problem can't masquerade as unmirrored CI debt.
- The `mirror` verb (crane install from a pinned release, one `crane copy {ref} {prefix}/{ref}` per declared reference, count footer) uses bashrun + plain prints — it needs nothing from any runner floor. Every declared reference is a target; nothing is filtered by prefix, so a drifted declaration cannot silently mirror zero.

The build-artifact-registry edge exists for the builds shelf: a `build --push` run distills bake's `--metadata-file` into a digest manifest (`target → {ref, digest, tags[]}` JSON) and pushes it through build-artifact-registry's `push_build` — one **shard** per matrix leg, tagged `sha-{full}-{key}` where the key is the sha256-8 of the leg's sorted targets (legs run in parallel, so a shared tag would be last-writer-wins; the pull side enumerates a SHA's shards and merges, and consumption only ever runs after every leg finished). The shelf root comes from the neutral `REGISTRY` environment and the SHA from the checkout HEAD (`git rev-parse HEAD`), stamping the certified PR head the release channels query back at; the keying law is stated in github-actions-toolkit's `AGENTS.md`. `workloads/images.lock` stays in source control (the stapler that consumed the shelf copy is gone). ORAS CLI knowledge lives only in build-artifact-registry (org law); local builds (no `--push`) never touch the shelf.

Lifecycle stays a separate package from codegen (client generation, datamodel generation, workspace locking) because their dependency surfaces are disjoint — bundling them would force a consumer that only brings a stack up to install `sqlacodegen`, `psycopg`, `datamodel-code-generator`.
